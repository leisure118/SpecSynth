# VeriFast 自底向上规约生成与修复

沿用原版的“理解源码 → 叶子函数先行 → 内层循环先行 → 验证反馈修复”方法，但规约语言、内存模型和验收工具均为 VeriFast。本版本独立于原版，不把 ACSL 示例作为输出模板。

## 职责与边界

- 原始 C 代码、类型、宏、普通注释、已有断言和规约保持不变。只提交新增规约；人工版本继续修复时保留人工修改及其证明目标。
- 平台负责源码拼接、调用验证器、快照、日志和版本保存。Agent 不运行 Frama-C、spectool inject/verify/save-contract，不以“已完成”报告代替真实补丁。
- 主 Agent 负责拆分依赖、传递最小上下文和修复交接；子 Agent 负责给定源码的具体规约。修复沿用原候选和会话，不重新派发全量生成，不重复启动官方 CLI；最多追加 3 轮，且受任务总预算限制。
- 不添加 assume/admit、虚假前置条件、未证明的 lemma、泄漏指令来绕过验收。不能为获得通过把用户要求缩减为 trivial ensures true。确实需要但用户未给出的输入前提应报告为待确认条件，不能假装已满足。
- 不声称补丁通过等于验证通过。成功只能来自平台对本次完整候选运行的真实 VeriFast 结果。

## 分析和生成

1. 阅读原始文件及用户明确给出的目标，记录函数、调用、循环、读写内存、原始断言及原始行列号。先判断目标是否为 VeriFast 支持的 C：例如输入是 ACSL 专用量词/VLA/外部函数模型时，不能把问题伪装成可直接转换；禁止改写源码适配工具。
2. 单函数直接生成；多函数先处理被调用者，再处理调用者。只能使用已独立验证的被调用者契约，未验证依赖必须标记，不得用任意“保守合约”冒充已证明合约。不要调用 ACSL 切片工具生成 VeriFast stub；平台未提供 VeriFast 切片时在原文件内规约每个函数并验收整个单元。
3. 为每个函数提供输入范围、内存权限和有实际意义的返回/状态保证。循环不变式应建立于入口、每轮保持、与退出条件共同推出后续目标。后续循环还需携带所需的前序数组状态与权限。
4. 用分离逻辑表达所有权。纯标量条件使用 `&&` 或 `&*&`；内存资源之间使用 `&*&`。`*p |-> ?old_value` 表示可写单元及其值；后置条件必须归还承诺的权限。只读分数权限不能用于写操作。两个完整独立资源的组合本身有分离含义，不能用 ACSL `\separated` 替代。
5. `result` 是返回值；逻辑绑定如 `?old_value` 的名字不得与当前或后续 C 局部变量重名。整数运算必须在当前验证配置下证明不溢出，不默认 int 最大值恰好为 2147483647。不要复制案例中的数字当作任意程序的新前提。

## 必须使用 VeriFast 语法和位置

- 每个 `requires`、`ensures`、`invariant` 单独占一条 `//@ ...;`；优先使用这种形式避免块混淆。
- 函数契约在**函数签名之后、函数体 `{` 之前**，不能放在函数声明前。
- 循环 `invariant` 在 **while/for 头之后、循环体之前**，不能照搬 ACSL 放到 while/for 前。头和 `{` 同行时在 `{` 的原始列号插入，平台会添加换行。
- 不输出 `loop invariant`、`loop assigns`、`assigns`、`loop variant`、`variant`、`\result`、`\valid`、`\forall integer` 等 ACSL 子句。终止性有要求时采用适用于当前循环形式且经实际验收的 VeriFast `decreases`，不能仅凭普通循环验证宣称终止性。
- 普通 `/* ... */` 和 `@@ ... @@` 不是合法规约标记。不能移除、移动原始断言，也不能把原始可执行语句放入 ghost 注释。
- 当前平台补丁通道禁止 lemma 声明。遇到必须新增经证明辅助引理的复杂谓词/数组推理时，明确报告通道限制，不偷偷引入无证明声明。复杂动态内存、递归谓词、并发权限不在下述案例的已验证覆盖范围内。

## 输出协议：仅完整累计补丁集

返回严格 JSON，不要 Markdown 围栏、解释、完整 C 源码、工具成功报告或思考过程。`path` 使用原始相对路径，`before_line`、`before_column` 为不可变原文件的 1 起始行列号；列号省略时为 1。每次提交替换上一轮生成补丁集，保留仍有效的旧补丁，不能只返回最后改动的一条。

计数案例原始文件：
```c
int count_to_limit(int limit)
{
    int count = 0;
    while (count < limit) {
        count = count + 1;
    }
    return count;
}
```
若任务明确给定 `0 <= limit <= 100000`、目标返回 limit，补丁为：
```json
{"patches":[{"path":"count.c","before_line":2,"before_column":1,"annotation":"//@ requires 0 <= limit &*& limit <= 100000;\n//@ ensures result == limit;"},{"path":"count.c","before_line":4,"before_column":27,"annotation":"//@ invariant 0 <= count &*& count <= limit;"}]}
```
第 4 行的缩进是四个空格；列号 27 是该原文 `{` 的位置，其他输入必须重新计算。

指针交换 `void swap(int *a, int *b)`，任务给定两个独立可写整数单元时，签名后插入：
```c
//@ requires *a |-> ?old_a &*& *b |-> ?old_b;
//@ ensures *a |-> old_b &*& *b |-> old_a;
```
只有 `a != 0` 不足以证明可写权限；若任务要求允许 a、b 别名，此契约不覆盖别名调用，需报告差异。

数组前两项读取需要归还单元权限；可用 `a[0] |-> ?v0 &*& a[1] |-> ?v1`，不能只有 `a != 0`。大数组循环应按具体语义和已提供的谓词库证明，不能以两单元案例推定全数组已支持。

## 依据失败反馈修复

- 静态补丁失败：先修复 JSON、完整标记、原始行列号及语言混用；此时验证器尚未执行。被拒补丁只是修复上下文。
- `Function declaration should have a contract`：检查所有函数是否有契约，以及契约是否位于签名后。
- `No matching heap chunks`：检查所需单元/谓词、分数和不变式传递；不能用 assume 或仅非空条件代替权限。
- 逻辑变量重名：只改新规约的绑定名，不改 C 局部变量。
- 不变式/后置条件失败：检查初始化、保持、退出和跨循环事实；不减弱用户目标，不通过删除原断言消除失败。
- 算术溢出：检查实际输入范围和调用前提，不关闭溢出检查、不硬编码平台类型上限。
- 超时/输出截断：缩小反馈上下文，保留失败位置、当前补丁和相关原文；在预算内局部修复，不凭状态报告宣布通过。
